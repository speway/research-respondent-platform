# Единый запуск формы из кабинета

## Рабочий порядок

1. Один раз сохранить фактическую базу, методики/ключи и документ основания.
2. Создать проект: источник, версия, ссылка Google Forms, ID, цель и отбор.
3. В «Автоматическое заполнение» выбрать проект/участника и режим.
4. Исполнитель сам открывает форму, читает видимые разделы, сопоставляет точные
   названия, проверяет значения и проходит по фактическому пути ветвления.
5. Журнал сохраняет результат; вкладку кабинета можно закрывать. Другой агент
   читает состояние этого проекта по существующему ключу чтения.

Режимы: `prepare` читает/проверяет первый доступный раздел без ввода; `fill`
проверяет и вводит по разделам без окончательной отправки; `submit` также
отправляет один ответ при подтверждённом источнике/участнике/получателе/основании.
Пилот: один участник за запуск, VM до 5 минут/1 vCPU, максимум 3 запуска за UTC
сутки на окружение, 100 сохранённых запусков на кабинет. Массовая очередь и
повторное использование разрешения для всего банка пока не реализованы.

## Как сокращаются действия

Оригинал уже хранится в кабинете, повторная загрузка не нужна. Для агента есть
`links.taskDownloadPath`: готовый JSON для импорта через интерфейс, когда его
браузер не разрешает выполнить JS-команду панели. Исходные байты и SHA-256
сохраняются. Новое необязательное `task.sourceRows` ограничивает исходные строки
и пересекается с прежними критериями; заголовки/значения/хеш не изменяются.
Один запущенный участник не блокируется пропусками других отобранных участников.
Исходные CSV локаторы и JSON индексы проверяются при загрузке/восстановлении.
Сохранение настроек сохраняет ограничение строк, а не расширяет его незаметно.

Механический исполнитель общий: `tools/browser-agent/runner.mjs`. Не используются
позиционные `nth-of-type` кнопки, фиксированная задержка 800 мс, изменение hidden
input, прямые запросы `formResponse`, догадки о психологических ответах, изменения
ответов под желаемую статистику или обход CAPTCHA. `Next` нажимается после сверки
каждого поля; переход проверяется по видимому состоянию. Методики с иными кодами
пунктов требуют подтверждённой карты соответствия, а не похожего названия шкалы.

## Облако и права

`POST /api/cabinet/automation` с `command:start` принимает `request` по схеме
`/.well-known/rrp-automation-command.schema.json`. Нужны выданная сессия кабинета,
JSON и тот же Origin. `requestId` надо сохранить при сетевой неопределённости:
его повтор возвращает прежний запуск. Новый ID с иным телом не должен служить
обходом неизвестного результата. После известного завершения можно явно начать
новую проверку. `command:cancel` с `jobId` просит остановку; если отправка уже
могла состояться, результат остаётся неопределённым, а не «отменённым».

`GET` без параметров — флаги/лимиты/журнал; `?project=<UUID>` — точные ID текущего
отбора и документы; `?job=<UUID>` — статус/прогресс/результат. Все закрыты сессией.
`GET /api/cabinet/agent?jobs=1` с проектным Bearer ключом возвращает только журнал
этого проекта и `mayStartOrSubmit:false`. Ключи не передаются в URL или логах.

Для `fill/submit` обязательны `evidenceAssetId`, `evidenceReference`,
`consentConfirmed:true`, `recipientConfirmed:true`. Проверяется доступность и
SHA-256 оригинала документа, источник/проект и принадлежность ID к отбору.
Подтверждение оператора записывается; это не автоматическая проверка содержания
согласия, его подлинности, срока, покрытия участников или совместимости старого
исследования с новым. Прежние ответы нельзя объявлять новыми наблюдениями.
Владелец должен подтвердить именно разрешённый перенос исходных ответов.

Исполнитель включается `RRP_FORM_AUTOMATION=1` на Vercel. Ввод/отправка требуют
`RRP_FORM_AUTOMATION_WRITE=1` в production; Preview допускает только `prepare`.
Старое SQLite хранилище этим не мигрируется и не разблокируется.

## Исполнение и журнал

Workflow получает только ID аккаунта/запуска, без ответов и ключей. Один create-only
маркер резервирует регистрацию, второй защищает старт VM. Внутри step читаются
оригиналы, выделяется непостоянная Sandbox без портов, устанавливается закреплённый
Playwright, затем разрешается сеть только к рабочей панели/Google-ресурсам.
Google-вход/CAPTCHA не автоматизируются. Google-куки, Vercel OIDC и постоянные
секреты в VM не передаются. При неизвестной регистрации/старте повторов нет;
step `maxRetries=0`, постоянная резервировка остаётся после ошибки.

Перед `Submit` worker пишет локальный запрос журнала. Сервер атомарно сохраняет
и перечитывает закрытый Blob маркер, только затем разрешает UI-клик. Локальный
файл VM здесь средство обмена, не долговременный журнал. Ключ дедупликации —
ID полной формы + постоянный ID участника, независимо от исходного хеша/аккаунта
и безопасных query-вариантов URL. Другие псевдонимы одного человека и альтернативные
публичные идентификаторы одной формы автоматически не объединяются.

После UI-клика нужны новое видимое подтверждение и исчезновение кнопки отправки.
Заранее присутствующий в вопросе текст «Ответ записан» отвергается. Неподтверждённая
отправка — `submission_uncertain`, повтор запрещён. При сбое после разрешения
журнала статус становится неопределённым даже если worker вернул общий `blocked`.
Итог/прогресс лежат в закрытом хранилище; ответы, исключения с их значениями и
скриншоты не пишутся в публичные логи. VM останавливается в `finally`; запись
счётчиков прогресса не содержит ответов. Панель опрашивает только активные задачи,
а не весь архив, и останавливает опрос после терминального результата.

`filled_not_submitted` — проверенные поля временной облачной вкладки. VM затем
закрывается; сохранённый Google-черновик или восстановление той вкладки не обещаны.
Продолжение с отправкой — новый явно разрешённый запуск с повторной проверкой.

## Пример команды

В авторизованном клиенте сайта (сессия остаётся на сайте, её не копируют агенту):

```js
const command = {
  command: "start",
  request: {
    requestId: crypto.randomUUID(), // сохранить и переиспользовать при неизвестном результате
    projectId: "UUID сохранённого проекта",
    participantRef: "ID из отбора проекта",
    mode: "prepare"
  }
};
const response = await fetch("/api/cabinet/automation", {
  method: "POST", credentials: "same-origin",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(command)
});
const job = await response.json();
if (!response.ok) throw new Error(job.error);
// Далее GET /api/cabinet/automation?job=<job.id>. Это не команда в Google Forms.
```

## Границы проверки

Доменные/интеграционные проверки покрывают область источника, повторную/конкурентную
регистрацию, лимиты, изменённые параметры, права/основания, истечение/отмену,
глобальный журнал, неизменяемость результатов и остановку VM. Chromium проверяет
реальный UI исполнителя на изолированной форме и кабинет с изолированным
транспортом. Успешный CI или подготовка первого раздела не доказывают полное
прохождение живой Google Forms. Фактический cloud run и выпуск документируются
в WORK_CONTINUATION.md. Нераспознанные формы/валидация, отсутствующие ответы,
карты кодов/методик и проверка согласия остаются блокирующими условиями.
